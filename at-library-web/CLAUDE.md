# at-library-web — заметки для быстрой работы

Дополняет [../CLAUDE.md](../CLAUDE.md) и [README.md](README.md). Здесь — тестовая архитектура модуля, конвенция написания шагов и найденные ловушки браузерных фикстур.

## Тестовая архитектура: раннеров несколько, не только RunFeaturesTest

Прежде чем делать вывод «этот шаг нигде не используется» — проверить **все** раннеры в `src/test/java/ru/at/library/web/`, не только основной:

| Класс | Теги/scope | Браузер | Назначение |
|---|---|---|---|
| `RunFeaturesTest` | `@unit` | да | основной функциональный suite (`src/test/resources/features/`) |
| `RunWebLocalStepContractTest` | без фильтра | да | `local-contract/web_steps_local_contract.feature` — реальный прогон на локальной JS-фикстуре для шагов, которым не подходит обычный сайт (загрузка файла, read-only форма, iframe, скрытые/disabled элементы) |
| `RunWebKnownGapContractIT` | без фильтра | да | `local-contract/web_known_gap_contract.feature` — **намеренно документирует 2 известных дефекта** (double-click не делает настоящий doubleClick; блочный вариант «клик + новая вкладка» не кликает элемент). Запускается отдельно, красный — это ожидаемо, не чинить как побочный эффект другой задачи |
| `RunWebStepCatalogTest` | `@unit`, `dryRun=true` | нет | быстрая regex-проверка (без браузера), что все `@unit`-шаги однозначно матчатся на step-definition |

`@manual`-каталоги (`blockcollection_steps_catalog.feature`, `catalog/web_steps_additional_catalog.feature`) и их выделенный раннер `RunBlockCollectionStepCatalogTest` **удалены** (2026-09-19) — были чистой документацией-дублированием того, что уже реально покрыто в `@unit`-сценариях; независимый аудит (скрипт: регэксп каждой `@И`/`@То`/`@А`-аннотации против каждой строки в feature-файлах, с корректным Java-unescape) подтвердил 285/285 покрытие без них.

## Основная браузерная фикстура — Wikipedia, не Google

`RunFeaturesTest` в основном ходит на `https://ru.wikipedia.org/?useskin=vector` (property `url.wikipedia`). Google остался живым источником только в `browser_steps.feature` (~34 сценария — cookies, вкладки, заголовки, кнопки вперёд/назад) и по историческим причинам считается менее приоритетным для миграции; часть сценариев там уже переведена на Wikipedia (переключение вкладок, «URL содержит», обновление страницы, ввод с клавиатуры). the-internet.herokuapp.com **не использовать** — пробовали, у него свои воспроизводимые проблемы (холодный старт, нестабильный размер коллекций).

### Ловушка: `#mw-panel` / `#p-lang`

Сайдбар Wikipedia (`#mw-panel`) содержит портлет `#p-lang` (интервики-языки) — на типичной странице это ~350 `<li>`, из которых видимо только ~10, остальные в свёрнутом `.vector-menu-content`, причём сворачивание происходит через JS уже после первичной загрузки DOM (асинхронно). Широкий селектор (`#mw-panel li`, или просто `li` внутри блока с корнем `#mw-panel`) на `List<CorePage>`-поле даёт многоминутное/бесконечное зависание (каждый скрытый элемент — полный таймаут на PRIMARY-проверку видимости), а на `ElementsCollection` со случайным индексом — нестабильный `IndexOutOfBoundsException`.

Используемый безопасный селектор (все видимые, все стабильные, ≥30 элементов, содержит нужные для существующих проверок тексты «Заглавная страница», «Избранные статьи», «Свежие правки» и т.д.):
```
#p-navigation li, #p-participation li, #p-coll-print_export li, #p-wikibase-otherprojects li
```
Используется в `WikipediaPage.linkList`/`navBlocks` и `WikiSidePanel.navBlocks`/`panelLinks`/`homeLink`. Не расширять обратно на `#mw-panel li` без повторной проверки скрытых элементов в браузере.

### Ловушка: `.click()` потом `.getText()`

Если клик по элементу может вызвать переход на другую страницу — **не** читать `.getText()`/другие свойства элемента после `.click()` (реальный источник `StaleElementReferenceException` в шагах со случайным/последним элементом списка — DOM успевает замениться раньше, чем выполнится чтение для лога). Читать нужные данные **до** клика.

### Ловушка: `CONTROL+a` → `BACK_SPACE` — гонка, а не баг

Два отдельных keydown (`Keys.chord(CONTROL,"a")`, затем отдельно `BACK_SPACE`) на обычном `<input>` — недетерминированная гонка браузера: иногда выделение успевает примениться (поле стирается полностью), иногда нет (стирается один символ). Подтверждено эмпирически на реальных прогонах. Не проверять точное итоговое значение после такой последовательности — проверять факт срабатывания (например, `не содержит текст "<исходное>"`).

### Ловушка: `текущий URL содержит` не читает `application.properties`

`BrowserSteps.checkContainsStringURL` резолвит значение через `PropertyLoader.loadValueFromFileOrVariableOrDefault` — путь к файлу, classpath-ресурс или переменная сценария, но **не** `application.properties`. Сценарий с пометкой «[PROPERTIES]» для этого конкретного шага исторически (ещё на Google) просто хардкодил литерал — не баг новый, унаследованная особенность.

## Конвенция объединения шагов «в блоке / без блока» («Technique A»)

Для пары шагов, отличающихся только наличием `в блоке "X" ...` в начале — **один Java-метод, две отдельные аннотации разных типов** (не одна аннотация с `(?:...)?`-группой, и не два экземпляра одного и того же типа):
```java
@И("^()в списке блоков \"([^\"]*)\" ... выполнено нажатие на блок$")
@А("^в блоке \"([^\"]*)\" в списке блоков \"([^\"]*)\" ... выполнено нажатие на блок$")
public void method(String blockName, String ...) { ... }
```
Короткий (без блока) вариант получает фиктивную пустую захватывающую группу `()` в начале, чтобы число групп совпадало с блочным вариантом.

Два независимых требования к IntelliJ Cucumber-плагину, оба подтверждены эмпирически:
1. Embedded-optional-group регекс (`(?:...)?`) работает для самого Cucumber, но ломает автодополнение шагов в плагине — подтверждено скриншотом.
2. **Тип аннотации не должен повторяться на одном методе**, даже с разными regex внутри. `@И`+`@И` на одном методе (то, как это было исторически почти everywhere до 2026-09-25) — плагин не видит эти шаги при подключении библиотеки как зависимости в другом проекте (через decompiled `.class` из установленного jar — так и поймали, при работе с исходниками в этом же репозитории проблема не проявляется). `@И`+`@А` — видит. Подтверждено скриншотом декомпилированного класса из реально собранного jar в проекте-потребителе.

Если у метода только два варианта (без блока / в блоке) — `@И` для первого, `@А` для второго. **Если вариантов четыре** (второе независимое измерение — например, «форма со значением в regex» / «docstring-форма без значения», или «наведение+клик» / «просто клик») — всем четырём аннотациям нужны четыре *разных* типа. Предпочитаем короткие: `И`, `А`, `То`, `Но` (в таком порядке — все по 1–2 символа). Сложившийся паттерн для пары «значение в regex / docstring-форма»:

| Вариант | без блока | в блоке |
|---|---|---|
| значение в regex | `@И` | `@Но` |
| docstring-форма (без значения в regex) | `@А` | `@То` |

Других коротких типов, кроме `И`/`А`/`То`/`Но`, в `io.cucumber.java.ru` нет — остальные (`Дано`, `Допустим`, `Если`, `Затем`, `Иначе`, `Когда`, `Ктомуже`, `Пусть`, `Также`, `Тогда`) длиннее, брать их только если реально нужно больше 4 разных типов на одном методе.

Быстрая проверка «нигде не задублировано» — сгруппировать подряд идущие Cucumber-аннотации над каждым методом и найти группы с повтором типа:
```bash
python3 -c '
import re, glob
ann = re.compile(r"^\s*@([А-Яа-яЁё]+)\(")
for path in glob.glob("at-library-*/src/main/java/**/*.java", recursive=True):
    g = []
    for i, line in enumerate(open(path, encoding="utf-8"), 1):
        m = ann.match(line)
        if m: g.append((i, m.group(1))); continue
        if g:
            names = [x[1] for x in g]
            if len(names) != len(set(names)): print(path, g)
            g = []
'
```
(пустой вывод = дублей нет).

Общая логика выбора блока/страницы — через приватный `resolveOwner(String blockName)`, диспетчеризующий по `blockName == null || blockName.isEmpty()` (непустая, но незаполненная группа даёт `""`, не `null`).
